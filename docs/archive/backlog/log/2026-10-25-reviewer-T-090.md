1. **목표가 실측 최고값보다 낮은 행 3개** — `docs/BENCHMARK.md` 4-1 B-05, 4-3 B-19, 4-5 B-32. 수정안: (a) B-19 목표를 ≤ 140ms로 올리거나, 허브 제외를 유지하려면 7절에 "예외: 최고값 미달 목표" 행으로 사유와 함께 옮긴다. 허브 포함 기준은 B-05·B-09·B-11·B-14·B-19 전부 같은 규칙으로 통일(4절 머리 "규칙"에 명시). (b) B-05는 2-2에 "첫 화면 비텍스트 375 / 1280" 행을 추가하고 그 최댓값을 최고값으로 쓴다(허브 16·23 포함 여부는 (a) 규칙대로). (c) B-32는 RealSelf 검토자 표기를 최고값으로 적고, 스펙(95 S0·T-022) 때문에 못 따라가면 7절 S4로 올린다.
2. **B-44 산술 불일치** — 4-7 B-44, 6절 P-03 6번. "FAQ 5~8 + 출처 펼침 1 + 구조화 데이터 토글 1"의 하한은 7 < 9. 수정안: FAQ ≥ 7로 쓰거나(00-product F5 5~8 안이므로 충돌 없음) 아코디언 추가 항목을 명시해 하한 합 ≥ 9로 맞춘다.
3. **90 3-9 갱신용 표 7행 중 2행 누락 + 바비톡 공개 가격 관찰이 스펙과 충돌하는데 미기록** — 3절 "90 3-9 표 갱신용 값", 7절. (a) "가격 출처·확인일"·"의사 정보" 2행 추가(2-2에 값이 이미 있음: O1b 가격 0·작성자/검토 0, 바비톡 허브 가격 있음·출처 0). (b) 2-2와 babitalk-procedure-375가 보여 주듯 바비톡 키워드 허브(O3)는 **로그인 없이 카드 가격·할인율·평점·후기 수를 노출**한다. 00-product 3-3 O3 관찰 "공개 가격 0(견적은 로그인 뒤)"·V1 "O3 가격·후기 로그인"과 정반대다. 3-3은 T-090이 잠정 칸을 확정하도록 했으므로 7절에 spec-question(S4: O3 관찰·V1 차별점 문구 정정)으로 올린다. 이 정정 없이 D8·V1에 "로그인 없이 가격"을 1순위 차별점으로 쓰면 바비톡을 매일 쓰는 심사자에게 바로 반박당한다.
4. **우리 측정 방법이 재현 불가** — 1절 "밀도"·"속도" 행, 4절 머리 "같은 스크립트". (a) 1절은 밀도가 "`scripts/check-density.mjs`와 같은 규칙"이라고 하지만 실제 측정 코드(`.playwright-mcp/bm-run.js` 12~14행)는 CSS 배경 이미지 포함, visibility·opacity 필터, 중첩 svg·picture 안 img 제외, 500px 지연 로딩 스크롤, 내부 스크롤 컨테이너를 쓰고, check-density는 그중 아무것도 하지 않으며 375 전용(1280 측정 불가 → B-13·B-14 검사 도구 없음). (b) "같은 스크립트"는 gitignore된 임시 파일이고 로그는 삭제를 요청했다. (c) 같은 page 객체로 375(콜드) → 1280(웜) 순서로 열어 1280 LCP는 웜 캐시 값이고, 바비톡 메인 375 944ms도 2회차(웜) 값인데 캐시 상태가 문서에 없다. 수정안: 측정 코드를 저장소 추적 경로(예: `scripts/bench-measure.mjs`, 경쟁사·우리 공용, 375·1280, 콜드/웜 옵션)로 옮기고 1절에 경로·캐시 상태·대기 시간·측정 위치(네트워크)를 적는다. check-density와의 차이를 표로 쓰거나 규칙을 맞춘다.
5. **속도 최고값이 1회 표본** — 1절 "속도", 4-3 B-15~B-19. 우리는 3회 중앙값으로 재는데 경쟁 최고값은 1회 값(바비톡 메인 2,212 → 944ms 편차 2.3배가 문서에 이미 있음). 188ms(B-16) 같은 목표가 한 번의 운 좋은 측정에서 나왔을 수 있다. 수정안: B-15~B-19 최고값을 정한 5개 URL만 같은 스크립트·같은 캐시 상태로 3회씩(15회, 바비톡 차단 한도 25회 안) 재측정해 중앙값으로 교체. 재측정이 불가하면 각 행에 "1회 표본" 표기와 우리 판정 시 허용 오차를 정의.

- 정적 HTML 보조(B) 방식은 헤드리스 차단 사이트를 기본 Node UA로 받는다. 위장은 아니지만 대상 경로의 robots.txt 허용 여부를 1절에 1줄 남겨 두면 심사자 질문에 답할 수 있다.
- B-22 "@type ≥ 12"는 타입 개수 자체가 목적이 될 위험이 있다(ScholarlyArticle 등 끼워 넣기). B-21 의료 타입 4가 본 목표이고 B-22는 "유효성 오류 0 조건에서" 같은 단서를 다는 편이 낫다.
- 측정 신뢰성 자체(바비톡 AI 검색, O1b JSON-LD)는 표본 2건 재측정에서 값이 정확히 일치했다. 측정 작업의 정확도는 높다.

## 5. 최종 질문 — 성형외과 마케팅 팀장이 이 벤치마크를 보면 "근거 있는 목표"라고 느끼는가?
**아직 아니오.** 구조(서비스×화면 실측표, 최고값→목표, 화면별 필수 요소, 저작권 고지)와 측정 정확도는 팀장이 납득할 수준이다. 아니오인 이유:
1. 바비톡 검색에서 가격이 로그인 없이 다 보이는데(이 문서 2-2가 직접 기록), 제품 정의서의 1순위 차별점 "로그인 없이 가격 확인"과 모순된 상태를 그대로 둔다 — 바비톡을 매일 쓰는 사람이 가장 먼저 찌를 지점(반려 3).
2. 국내 상담의 주 경로인 카톡상담을 빼고 "상담 마찰 6클릭 vs 우리 5클릭"을 비교한다(반려 6).
3. 188ms·412ms 같은 속도 목표가 무쓰로틀 1회 측정에서 나왔고, 우리 측정 스크립트는 저장소에 없다 — "그 숫자 다시 재 보세요" 하면 재현할 방법이 없다(반려 4·5).
4. 허브 제외·FAQ 하한 등 목표를 낮추는 쪽으로만 기준이 흔들린 행이 있다(반려 1·2).
