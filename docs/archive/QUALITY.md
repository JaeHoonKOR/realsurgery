# 품질 기준 (Definition of Done) — v2  (= docs/specs/80-quality.md)

> 규범: 디자인 규칙은 10-design, 트래킹 이벤트는 40-tracking, 제출물은 90-deliverables이 원본이다. 이 문서는 **게이트·검수 절차**만 규정한다. 6절은 10-design 완본 전까지의 임시 규칙.

## 0. 왜 이 기준인가
이 사이트는 **성형외과 개발·마케팅 팀이 심사하는 채용 포트폴리오이자 실제 수익 서비스**다. 심사자는 매일 강남언니·바비톡·여신티켓을 쓴다. 그들이 "우리 사이트보다 낫다"고 느껴야 하고, 공고 요건 5가지(SEO·AEO·GA4/GTM 트래킹·검색광고 분석·메타광고)가 **화면에서 보여야** 한다. 테스트 통과·Lighthouse 점수는 전제 조건이지 완료 조건이 아니다.

**최종 질문(리뷰어가 매번 답한다)**: "이 화면을 성형외과 마케팅 팀장에게 보여줬을 때, 이 사람을 채용하고 싶은가?" 아니오면 사유 3개 이상 적어 반려.

## 1. 흐름이 먼저다 (마일스톤 M1)
화면 단위 완료는 없다. **예외(느린 신호)**: T-400(색인 제출)·T-200/201(트래킹)·T-402(AEO 측정)·T-500(광고 워밍업)은 M1과 병렬로 진행한다 — 결과가 나오는 데 2~4주 걸리기 때문. **배포 URL에서** 아래 흐름이 클릭만으로 끝까지 이어져야 M1이고, M1 전에는 어떤 작업도 `done`이 아니다.
```
메인 → 시술 검색/카드 클릭 → 시술 가이드 → 병원 카드 → 병원 상세 → 상담 가이드 받기(2단계) → 완료
                                    ↘ 중간 CTA → 상담 폼
```
- 모든 카드·목록 항목은 **링크**다. 글자만 있고 클릭 안 되는 요소는 반려.
- 404·빈 화면·링크 없는 화면 1개라도 있으면 M1 실패.
- 리뷰어는 이 흐름을 **Playwright로 배포 URL에서 직접 클릭**하며 단계마다 스크린샷을 찍는다. 저장된 스크린샷 파일로 판정하지 않는다.

## 2. 벤치마크 이상 (docs/BENCHMARK.md가 기준)
T-090에서 강남언니·바비톡·여신티켓·RealSelf·Zocdoc를 실제로 열어 분석한 `docs/BENCHMARK.md`의 "우리가 넘어야 할 항목"을 화면마다 체크한다. 요지:
- **3초 규칙**: 첫 화면(375×812 첫 스크롤, 1280×800 첫 스크롤)에 가치 제안 1문장 + 실데이터 카드 ≥ 2 + 신뢰 수치 ≥ 1 + 주 CTA 1개.
- **밀도**: 375×667 스크롤 구간마다 텍스트 외 요소(이미지·SVG 다이어그램·차트·아이콘 카드) ≥ 2. 0인 구간 = 반려.
- **데이터가 살아 보인다**: 가격은 분포 바/범위 바, 회복은 타임라인, 병원은 비교 바, 출처는 "n개 교차검증" 뱃지. 숫자를 표로만 보여주면 반려.
- **마이크로 인터랙션**: 카드 호버 상승, 아코디언 애니메이션, 스크롤 진행 표시(가이드), 폼 단계 전환, 완료 애니메이션, 스켈레톤 로딩. `prefers-reduced-motion` 존중.
- **쿠키 배너**: 하단 1줄(높이 ≤ 64px), 본문 가리지 않음.
- **워드마크 로고 SVG**, 시술별 일러스트(Gemini, 얼굴 없음), 부위 아이콘, 빈 상태 일러스트.

## 3. 공고 요건이 화면에서 증명된다 (차별점)
| 요건 | 화면에서 보이는 증거 | 작업 |
| --- | --- | --- |
| SEO·JSON-LD | 모든 페이지 하단 "이 페이지의 구조화 데이터" 토글 → JSON-LD 예쁘게 출력 + 리치 결과 테스트 링크 | T-120 |
| AEO | 가이드 상단 "AI 답변용 요약" 박스(직답 2~3문장, 복사 버튼) + llms.txt 링크 | T-103 |
| GA4/GTM | 완료 화면 "이 전환은 이렇게 기록됩니다" 블록(이벤트명·파라미터·GTM 태그명) | T-102 |
| 검색광고·메타광고 | 공개 **인사이트 페이지** `/insights`: 퍼널(view→form_start→lead), 유입 채널, 키워드 순위, AEO 인용률, CPL — 키 없을 땐 "데이터 수집 중" 상태와 구조만 | T-121 |

## 4. 자동 게이트 (전제 조건, 통과해도 완료 아님)
| 항목 | 기준 |
| --- | --- |
| Lighthouse 모바일 | Perf ≥ 90, A11y ≥ 95, BP ≥ 95, SEO 100, LCP ≤ 2.0s, CLS ≤ 0.05 |
| axe | critical·serious 0 |
| 타입·린트 | 0 error, 0 warning |
| 단위 | 커버리지 ≥ 80% |
| E2E | **M1 흐름 전체**가 배포 URL과 로컬 둘 다에서 통과(`tests/e2e/flow.spec.ts`), 375·1280 |
| 콘솔 | error·warning 0 |
| 링크 | 깨진 내부 링크 0, 클릭 불가 카드 0 (`scripts/check-links.mjs`) |

## 5. 상태 커버리지
로딩(스켈레톤)·빈(일러스트+안내)·에러(원인+해결 1문장)·성공. 폼: 인라인 검증, 제출 중 비활성, 중복 방지, 실패 시 값 보존.

## 6. 디자인 규칙
토큰 1곳(색 ≤ 8, 간격 4px 배수), Pretendard, 본문 16/1.7, 제목 3단계, keep-all, 터치 44px, 콘텐츠 최대폭 1120px, 본문 680px. 금지: 보라 그라디언트, 아이콘 3개 나열, lorem, 기본 Tailwind 파랑, 이모지. 병원명은 가상 + `is_demo` 표기.

## 7. 작업 순서 (모든 화면 공통)
1. **레이아웃 명세** `docs/layouts/<ID>.md`: 섹션 순서, 각 섹션의 비주얼(어떤 이미지·차트·아이콘), 인터랙션, 데이터 필드, 375/1280 와이어(ASCII). BENCHMARK 대조표 포함. → reviewer가 먼저 승인.
2. 구현.
3. 자가 검증: 4절 게이트 + **배포(또는 로컬 dev) URL을 Playwright로 열어 M1 흐름 중 해당 구간 클릭**.
4. reviewer: 1절 흐름 클릭 + 2·3·6절 대조 + 최종 질문. 승인 → main 머지 → 배포 → **배포 URL에서 재확인** 후 done.

## 8. 리뷰어 절차 (스크린샷 파일 판정 금지)
1. `pnpm dev`(또는 배포 URL)를 Playwright로 연다. 375×812, 1280×800.
2. M1 흐름을 순서대로 클릭한다. 단계마다 스크린샷을 **그 자리에서** 찍어 Read로 본다.
3. 각 화면에서 센다: 이미지 수, SVG 수, 링크 수, 클릭 불가 카드 수, 375×667 구간별 비텍스트 요소 수. 하한 미달 = 반려.
4. BENCHMARK.md 대조표를 채운다(항목별 우리/벤치마크/판정).
5. 최종 질문에 답한다. 아니오면 사유 3개 이상.
6. 4절 게이트를 직접 재실행한다.
